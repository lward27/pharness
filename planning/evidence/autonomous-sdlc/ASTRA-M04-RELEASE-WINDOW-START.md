# ASTRA M04: Start release observation from fresh rollout telemetry

The first sourcee508 ten-minute [service window](ASTRA-MEASUREMENT-ALIGNMENT-RELEASED-SERVICE-WINDOW.json) is retained as `inconclusive_or_failed`. All 21 direct API/UI samples succeeded. The first of 21 API-availability metric values was zero; its other 20 values and all 21 values for the four other Deployments were one. The collector stopped at that failed predicate, so the remaining query and final-snapshot checks were not completed by that attempt. No model call followed it.

[Timestamp diagnosis](ASTRA-MEASUREMENT-ALIGNMENT-WINDOW-START-DIAGNOSIS.json) establishes the sequence: the underlying zero-valued sample was scraped at 16:41:15.185 UTC; Kubernetes recorded API availability at 16:41:21; exact live identity was verified at 16:41:45.239; the window began at 16:41:59.359. Its first range-query point therefore selected a sample 44.174 seconds old, predating availability by 5.815 seconds. The next query point selected the positive sample scraped at 16:42:15.185. This supports a window-start measurement mismatch, not a demonstrated API regression during the observation period.

Prometheus evaluates a range query at successive requested times and selects the most recent underlying sample at or before each time. The returned query timestamp is not itself proof of a new scrape. [Prometheus query semantics](https://prometheus.io/docs/prometheus/latest/querying/basics/#staleness).

The [revised procedure](ASTRA-MEASUREMENT-ALIGNMENT-WINDOW-PROCEDURE-CHANGE.json) adds a pre-window check: all expected availability series must be positive, at most 90 seconds old, and have underlying sample timestamps after the verified rollout observation. It writes a separate R2 record. The full 600-second duration, 30-second cadence, identity, availability, freshness, restart, log and warning predicates are unchanged. No first sample is discarded, no timestamp shifted in the failed result, and no window shortened. Current fresh availability passed the added precondition before the new window began.

The first script-comparison check accidentally normalized the filename of an existing historical R2 query source as well as the new output filename. A corrected output-specific comparison proves the remaining collector body is unchanged. The already-started read-only R2 collector was retained; it was not dispatched twice. The original failed receipt and its hash remain preserved.

The separate [new full window](ASTRA-MEASUREMENT-ALIGNMENT-RELEASED-SERVICE-WINDOW-R2.json) now passes with 21 direct samples, all required metric/log checks, stable identities and no new Pod warnings. Fresh protocol/evaluation calls were held until that result. This correction belongs in the release procedure; healthy direct probes alone cannot replace the telemetry gate. It changes no PHarness runtime, infrastructure, model setting or Finance authority.
