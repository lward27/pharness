The harnessMoving a WorkItem through the harness

The operator works from a Product and a bounded WorkItem. A WorkItem is one bounded engineering intent and its complete lifecycle record: applicable stages, plans, executions, approvals, evidence, source delivery, and any connected release work.

The lifecycle at a glance

Each WorkItem moves through a small state machine enforced by the API (work-items transition validates every move):

proposed→ submitted→ planning→ awaiting_approval→ executing→ verifying→ completed
StateAllowed next states
proposed / submittedplanning, cancelled
planningawaiting_approval, blocked, failed, cancelled
awaiting_approvalexecuting, blocked, failed, cancelled
executingverifying, blocked, failed, cancelled
verifyingcompleted, waiting_external, blocked, failed, cancelled
waiting_externalcompleted, blocked, failed, cancelled
blocked / failedplanning, awaiting_approval, cancelled
completed / cancelledterminal — no transitions
Stages vs. states

The lifecycle states above track the WorkItem. Inside it, the deterministic controller works stage by stage: discover → plan → implement → test → verify → source_delivery → release → observe. Each terminal stage execution produces an immutable, controller-sealed StageOutcome (succeeded, failed, blocked, cancelled, or inapplicable). An agent may propose a summary but cannot seal its own success — the controller adjudicates against typed evidence before the WorkItem advances.

When to create a new WorkItem

A replan stays in the same WorkItem while the desired outcome, mutable repository, and acceptance boundary remain the same. Create a new linked WorkItem (with a typed relationship like supersedes, follows_up, or discovered_from) when the operator materially changes the outcome, the mutable repository or delivery target, or the acceptance boundary. A hosted WorkItem mutates exactly one application repository; other repositories may only be pinned read-only.

Step 1 — Create the WorkItem

Register intent with acceptance criteria up front. This is what the controller later verifies — vague criteria produce vague outcomes.

cargo run -p pharness-cli -- work-items create \
  --title "Add rate limit to public API" \
  --intent "Enforce a per-client token bucket on the public API endpoints so a single client cannot exhaust model quota." \
  --acceptance-criterion "Requests over the limit return 429 with a Retry-After header" \
  --acceptance-criterion "The limit counter resets each 60s window" \
  --acceptance-criterion "cargo test --workspace passes unchanged" \
  --source-repo https://github.com/lward27/pharness \
  --source-ref main \
  --target-environment dev \
  --actor lucas

Key flags:

FlagMeaning
--acceptance-criterion (repeatable)Each independently testable criterion. The verify stage checks exactly these.
--source-repo / --source-refThe mutable application repository, exact HTTPS URL. The mutable repo + pinned revision are immutable WorkItem inputs.
--gitops-repo / --gitops-refOptional separate GitOps delivery repository (for hosted delivery).
--target-environment / --target-namespace / --argo-applicationWhere the outcome should land. Dev targets first — production is separately gated.
--production-impactingSet only if the change can affect production; it tightens approval requirements.
--max-attempts / --max-elapsed-secondsBudget caps for bounded retries.
--actorAttribution for audit events.
# Inspect what you created
cargo run -p pharness-cli -- work-items list
cargo run -p pharness-cli -- work-items get --work-item-id <id>

Step 2 — Plan

Move the item into planning. An ephemeral Planner AgentRun proposes the WorkPlan; the proposal must declare readiness (ready with an empty blocker list, or needs_decision with concrete blockers). A blocked proposal is retained with its blockers — resolve the blocking choice with an annotation, then replan.

cargo run -p pharness-cli -- work-items transition \
  --work-item-id <id> --target-status planning --actor lucas

cargo run -p pharness-cli -- work-items get --work-item-id <id>   # inspect the plan
cargo run -p pharness-cli -- work-items create-work-plan --work-item-id <id>  # WorkPlan + declared workspace

If the plan needs operator input, use replan to schedule one remaining bounded retry after a failed or blocked attempt:

cargo run -p pharness-cli -- work-items replan \
  --work-item-id <id> --actor lucas --reason "operator approved the proposed approach"

Step 3 — Approve and execute the coding attempt

Approving the plan moves the item to executing. execute provisions an isolated local clone under workspace_root and starts one bounded coding attempt. The clone is isolated: Pharness never pushes, merges, or touches your source checkout from the workspace.

cargo run -p pharness-cli -- work-items transition \
  --work-item-id <id> --target-status awaiting_approval --actor lucas

cargo run -p pharness-cli -- work-items transition \
  --work-item-id <id> --target-status executing \
  --actor lucas --reason "plan reviewed and approved"

cargo run -p pharness-cli -- work-items execute \
  --work-item-id <id> --actor lucas \
  --max-turns 40    # optional budget cap

While it executes: approvals

The policy mode decides what the agent must ask permission for. The default local policy requires approval for writes, network, and destructive operations, and denies secret access outright. Watch the queue:

cargo run -p pharness-cli -- approvals list            # pending + decided
cargo run -p pharness-cli -- approvals summary         # counts by status/kind/risk
cargo run -p pharness-cli -- approvals get --approval-id <aid>
cargo run -p pharness-cli -- approvals approve --approval-id <aid>
cargo run -p pharness-cli -- approvals deny --approval-id <aid> --reason "out of scope"
Deny by default

Only approve what you understand from the approval detail. A network approval means the runner may reach the listed hosts during that run — the runner itself has no direct internet egress in the deployed runtime; it goes through the phase-specific CONNECT proxies with server-owned exact-host allowlists.

Step 4 — Verify

When the coding attempt finishes, transition to verifying. The controller runs the declared acceptance commands against the workspace and seals a StageOutcome against your acceptance criteria. Inspect the evidence before moving on:

cargo run -p pharness-cli -- work-items transition \
  --work-item-id <id> --target-status verifying --actor lucas

cargo run -p pharness-cli -- work-items get --work-item-id <id>      # stage outcomes, evidence refs
cargo run -p pharness-cli -- work-items events --work-item-id <id>   # audit trail
cargo run -p pharness-cli -- runs get --run-id <rid>                 # the agent run
cargo run -p pharness-cli -- runs diff --run-id <rid>                # stored file diffs
cargo run -p pharness-cli -- artifacts list --run-id <rid>
What counts as verified

Verified facts are bound to typed evidence: exact acceptance command, execution identity, exit result, captured output reference. Agent claims that could not be independently verified are labeled as claims, not facts. Missing runtime telemetry is inconclusive, never a pass. If the outcome is blocked or failed, the item returns to planning or awaiting_approval — replan, don't force it.

Step 5 — ChangeSets, pipeline, and delivery

Once verification succeeds, derive the proposed ChangeSet from the workspace diff, then drive delivery. The delivery chain is a sequence of durable, individually audited records — each with its own approval gate:

# 1. Derive the proposed ChangeSet from the latest completed workspace diff
cargo run -p pharness-cli -- work-items capture-change-set \
  --work-item-id <id> --actor lucas
cargo run -p pharness-cli -- change-sets list
cargo run -p pharness-cli -- change-sets get --change-set-id <csid>   # review before anything applies

# 2. Propose a PipelineIntent from the approved, immutable merged source revision
cargo run -p pharness-cli -- work-items create-pipeline-intent \
  --work-item-id <id> --pipeline-contract-id <pcid> --actor lucas
cargo run -p pharness-cli -- pipeline-intents list
cargo run -p pharness-cli -- pipeline-contracts list

# 3. Review the deployment contract, then execute the deployment intent
cargo run -p pharness-cli -- deployment-contracts list
cargo run -p pharness-cli -- deployment-intents list
cargo run -p pharness-cli -- deployment-intents execute --apply \
  --deployment-intent-id <diid> --actor lucas

# 4. Watch approvals and external waits
cargo run -p pharness-cli -- approval-gates list
cargo run -p pharness-cli -- work-items waits --work-item-id <id>
cargo run -p pharness-cli -- work-items reconcile-due-waits --actor lucas

For an inert, safe end-to-end rehearsal of the delivery path (creates durable test records, changes no application, reads no secret):

export PHARNESS_API_TOKEN='your operator token'
scripts/pharness-tekton-execution-smoke.sh            # preflight — stops before any PipelineRun
scripts/pharness-tekton-execution-smoke.sh --apply    # dispatch the single inert PipelineRun
Console equivalent

The Lamina console offers the same flow: Delivery Test → review fixture scope → Prepare preflight → confirm Preflight Passed → Dispatch inert PipelineRun → wait for Completed → Open delivery flow to inspect the WorkPlan, ChangeSet, PipelineIntent, approval gates, audit events, and PipelineRun receipt. A terminal succeeded receipt is an execution result, not a deployment approval — the executor also persists a bounded PipelineRunAnalysis whose satisfied evidence is required before a DeploymentIntent can approve.

Step 6 — Complete or recover

# Success path: verifying → waiting_external (e.g. merge check) → completed
cargo run -p pharness-cli -- work-items transition \
  --work-item-id <id> --target-status waiting_external --actor lucas
cargo run -p pharness-cli -- work-items transition \
  --work-item-id <id> --target-status completed --actor lucas \
  --reason "acceptance criteria verified; delivery evidence sealed"

# Failure path
cargo run -p pharness-cli -- work-items transition \
  --work-item-id <id> --target-status failed --actor lucas \
  --reason "acceptance command X fails: <output ref>"
# then: replan (same intent) or create a new linked WorkItem (changed intent)

# Abort at any non-terminal state
cargo run -p pharness-cli -- work-items cancel \
  --work-item-id <id> --actor lucas --reason "no longer needed"
Source-only vs. deployed

Source merge, deployment, and verified runtime behavior are distinct results. Legacy source-only success remains valid history but does not imply anything was deployed. New hosted WorkItems remain nonterminal until the approved target has deployed and runtime acceptance is verified. Production GitOps merge requires human approval bound to the exact artifact and evidence.
