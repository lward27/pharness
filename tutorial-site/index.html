Getting startedOperating PHarness

PHarness is an SDLC control plane: one bounded request (a WorkItem) progresses through coding, tests, source delivery, immutable builds, staging, human production approval, and runtime verification. You operate it from the pharness CLI, the API, and the Lamina operator console.

How to read this site

Page 1 (here) — build and test the codebase locally. Page 2 — move a WorkItem through the coding harness. Page 3 — build, pin, and verify a release. Page 4 — reference material.

Prerequisites

The workspace contains the Rust runtime, API, store, workers, model gateway, evaluator, CLI, and the React/Vite console under ui/. You need:

ToolUsed for
rust (workspace pins rust-version = "1.80", see rust-toolchain.toml)Building and testing all crates
node / npmThe console UI in ui/ (Vite + Vitest)
docker + a buildx builderRelease image builds (page 3)
helm, jq, kubectlRelease pinning and cluster operations

Environment variables you will use throughout (never write secret values into playbooks or transcripts):

export PHARNESS_API_URL=http://127.0.0.1:4777   # where the API is listening
export PHARNESS_API_TOKEN=<operator token>      # deployed APIs require it; local loopback APIs ignore it

Build locally

  1. Check formatting 
    cd ~/Personal/pharness
cargo fmt --all -- --check
  2. Lint the whole workspace 
    cargo clippy --workspace --all-targets -- -D warnings
  3. Build everything (debug is fine for local work) 
    cargo build --workspace

    Binaries you care about live in target/debug/:

    BinarySource crateRole
    pharnesspharness-cliMachine-facing control CLI (your main operator tool)
    API binarypharness-apiAxum control-plane API, default bind 127.0.0.1:4777
    pharness-workerpharness-workerLocal-process execution of coding runs and egress proxy
    pharness-adminpharness-api binAdmin/maintenance operations
Module boundaries

Before changing API app code, run the architecture guardrails: scripts/check-app-module-boundaries.sh. Fixes must preserve the single-writer database and scoped reader/writer/effect responsibilities. For UI work, follow ui/AGENTS.md.

Test locally

  1. Rust test suite 
    cargo test --workspace

    Every crate has tests; the deterministic replay and stage-outcome logic in particular must stay green. A subset is fast:

    cargo test -p pharness-core      # stage model, repo mode, inference grants
cargo test -p pharness-runhost   # command sandboxing, workspace validation
cargo test -p pharness-api       # app routes and auth
  2. UI checks 
    cd ui
npm ci
npm test            # vitest run
npm run build       # vite build
npm run dev         # console at http://127.0.0.1:5173

    The CORS origin in config defaults to http://127.0.0.1:5173, so a locally served console talks to a locally bound API with no extra setup.

  3. Start a local API and poke it

    Copy the example config, start the API, then use the CLI against it:

    cp config/pharness.example.toml ~/.config/pharness/config.toml
# adjust [model] (provider/api key env) and [storage] as needed
cargo run -p pharness-api &          # listens on 127.0.0.1:4777 by default

export PHARNESS_API_URL=http://127.0.0.1:4777
cargo run -p pharness-cli -- config          # inspect/validate configuration
cargo run -p pharness-cli -- runs list       # inspect persisted runs
cargo run -p pharness-cli -- work-items list # inspect durable work items
Local vs. deployed

Local execution ([execution] target = "local_process") remains useful for development; it is not the primary product promise. The deployed runtime runs workers as Kubernetes Jobs. Treat a locally successful run as a development signal, not release acceptance — never infer release acceptance from readiness or Argo health alone.

Local configuration

Local runtime configuration is illustrated in config/pharness.example.toml. The sections that matter day to day:

SectionKey fieldsNotes
[model]provider, model, api_key_env, tool_protocolWhich model serves coding runs. The key comes from the named env var, never the file.
[agent]max_turns, max_context_tokensBudgets for one agent run.
[execution]target = local_process | kubernetes_jobWhere coding runs execute.
[storage]kind = "sqlite", path, workspace_root, workspace_allowed_reposSingle-writer SQLite store. Real coding only clones repos listed here, into an isolated workspace under workspace_root; Pharness does not push, merge, or touch the source checkout.
[policy]mode = default | trusted_writes | plan | deny_all_writesApproval requirements for writes, network, destructive ops; secret access denied.
[api]bind, cors_originLoopback bind by default.

See Config reference for the full tour, including the [worker.kubernetes] identities (git writer, GitOps writer, observer, Argo runner) and their disabled-by-default posture.
