ReferenceCLI cheat sheet

The pharness CLI is the machine-facing control surface. Every command accepts --api-url (default http://127.0.0.1:4777, env PHARNESS_API_URL) and attaches Authorization: Bearer $PHARNESS_API_TOKEN when that env var is set. Deployed APIs require the token; local loopback APIs ignore it.

Troubleshooting

SymptomLikely cause / check
cannot transition work item from X to Y (409) Invalid move in the WorkItem state machine. Check the allowed transitions on the lifecycle page; from blocked/failed you must return to planning or awaiting_approval, not verifying.
Planner run returns needs_decision Expected: the proposal has concrete blockers. Read them, add an operator annotation, then work-items replan. A blocked proposal is retained with its blockers — never inferred ready.
releases verify returns attention_required Expected safety outcome: the target is unhealthy or still progressing. Inspect the returned observation ids and the release audit trail; do not force --complete.
Build preflight fails: "build preflight did not return the requested immutable revision" The revision must be the exact current merged origin/main (40-char lowercase SHA). Re-fetch and re-resolve.
Build preflight: builder error The builder name must be an explicit, reachable buildx builder (e.g. rancher-desktop). No fallback is permitted — create/inspect it with docker buildx ls.
Release pinning: "release pinning requires a clean worktree" Commit or stash changes first; the script refuses to pin over a dirty tree.
Release pinning: "rendered release contains a mutable Pharness image" A :latest tag survived in the rendered chart. The pin script should have replaced every digest — check the diff it printed and re-run from a clean tree.
UI won't talk to the API Check [api].cors_origin matches the console origin (default http://127.0.0.1:5173); for deployed APIs, set PHARNESS_API_TOKEN and confirm the API is reachable at PHARNESS_API_URL.
unsupported work item status transition --target-status must be one of: proposed, submitted, planning, awaiting_approval, executing, verifying, waiting_external, blocked, completed, failed, cancelled.
Stage outcome blocked mid-execution A required input, capability, policy decision, authorization, or external condition is unsatisfied. Check work-items waits and the approval queue; reconcile due waits against persisted evidence only.

Safety rules (non-negotiable)

  1. Never copy credentials into playbooks, command transcripts, or docs. Tokens come from env vars or mounted Secrets; the API never reads writer token Secrets itself.
  2. State the effect boundary before any effectful operation — exact cluster context, namespace, target, expected mutation, success criteria, and cleanup ownership.
  3. Never infer acceptance from readiness or Argo health alone. Typed verification with durable evidence is the bar.
  4. Agents cannot seal their own success. The controller adjudicates against typed evidence; agent claims stay claims.
  5. A missing or stale evidence record is recorded honestly. Absence of a failing record is never converted into success.
  6. Production requires human approval bound to the exact artifact and evidence. Rollback restores service; it does not make the WorkItem succeed.
  7. Manage deployments through their GitOps sources. Hand kubectl apply on production is the direct_apply_break_glass escape hatch, not a workflow.
  8. Preserve the single-writer database and scoped reader/writer/effect responsibilities when changing code — run scripts/check-app-module-boundaries.sh.
