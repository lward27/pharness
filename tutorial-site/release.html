ReleasingFrom verified source to verified runtime

A Release is an immutable promoted outcome for one Product and Environment. It binds the promoted source and artifact provenance, the applicable WorkItems, deployment evidence, verification result, and rollback relationship. A source pull request or merge is not a Release. Within one release, a single real build feeds distinct staging and production deployment records — promotion never creates a fictitious second build.

Build the release images

The current PHarness release builds seven images from one exact merged source revision: runtime, UI, Python runner, Node runner, model gateway, evaluation runner, and the Codex-host image. The build entry point requires an explicit builder; there is no fallback.

  1. Pick the exact merged revision 
    git fetch origin main
REVISION=$(git rev-parse origin/main)   # full 40-char lowercase SHA
  2. Run a preflight (no images pushed) 
    scripts/pharness-build.sh all \
  --revision "$REVISION" \
  --builder rancher-desktop \
  --preflight-only

    The preflight verifies the revision against the configured remote/branch, confirms the buildx builder is reachable, and runs an uncached linux/amd64 platform-execution probe — the authoritative gate for emulated builders (VZ/Rosetta can execute amd64 correctly while BuildKit reports only the native worker platform).

  3. Build and push all seven 
    scripts/pharness-build.sh all \
  --revision "$REVISION" \
  --builder rancher-desktop

    Each component is pushed to registry.lucas.engineering with a git-<sha> tag, and the script verifies the returned sha256: digest, the registry manifest digest, the linux/amd64 architecture, and the OCI org.opencontainers.image.revision label before accepting it. The JSON lines it prints carry the digest per component — save them; the pinning step needs all seven. all and codex-host targets also build the native host bundle.

What a digest is — and isn't

A digest identifies an artifact. It is not by itself an SBOM, signature, or vulnerability attestation. The build records sbom_verified: false / signature_verified: false / provenance_verified: false by design; treat those as open follow-ups, not as implicit guarantees.

Pin the release (GitOps)

After all seven images are built, prepare the separate Helm release commit. The script does not commit, push, merge, or sync Argo — those remain reviewed operator actions.

scripts/pharness-release-pin.sh \
  "$REVISION" \
  "$RUNTIME_DIGEST" \
  "$UI_DIGEST" \
  "$PYTHON_RUNNER_DIGEST" \
  "$NODE_RUNNER_DIGEST" \
  "$MODEL_GATEWAY_DIGEST" \
  "$EVAL_RUNNER_DIGEST" \
  "$CODEX_HOST_DIGEST"

What it does, in order:

  • Requires a clean worktree and that $REVISION equals the current merged origin/main.
  • Replaces every digest:/revision: field in deploy/helm/pharness/values.yaml for the api, ui, inference gateway/evaluation, and Codex backend sections.
  • Updates the agent execution registry (deploy/helm/pharness/files/agent-execution-registry.json) with the Python/Node/eval runner digests and checks it.
  • Runs helm lint, renders the chart, and fails if any mutable :latest Pharness image remains or any expected digest is missing from the rendered output.
  • Prints the final diff for your review.
# Review the diff, commit it on a separate release branch, and merge it
# manually before Argo sync.
git diff -- deploy/helm/pharness/values.yaml \
          deploy/helm/pharness/files/agent-execution-registry.json
git add -A && git commit -m "release: pin $REVISION"
git push origin HEAD:release-<date>   # then open and merge the PR manually
Manage deployments through their GitOps sources

Never kubectl apply a production change by hand, and never infer release acceptance from readiness or Argo health alone. A range-query timestamp alone can still select an older pre-readiness sample — confirm the underlying sample timestamps follow the verified rollout before starting an observation window, and retain failed or interrupted windows separately.

Verify a release (dev, read-only first)

After a disposable development WorkItem has completed a real Argo sync through deployment-intents execute --apply, run the typed read-only verification. The verifier requires durable WorkItem ownership and an exact declared Deployment target; it performs typed reads only — it cannot request an Argo sync, patch a Kubernetes resource, run a shell command, or read a secret.

  1. Select an approved dev Release 
    cargo run -p pharness-cli -- releases list \
  --status approved --target-environment dev --limit 20
export RELEASE_ID=rel_<the-approved-dev-release-id>

cargo run -p pharness-cli -- releases get --release-id "$RELEASE_ID"
# expect: status=approved, target_environment=dev, your namespace + Argo app
  2. Run read-only verification 
    cargo run -p pharness-cli -- releases verify \
  --release-id "$RELEASE_ID" --actor lucas --timeout-ms 30000
# expect: status=verified, verified=true, completed=false
#   Argo:  sync_status=Synced, health_status=Healthy
#   Workload: status=healthy
#   (if the contract requires it: prometheus_inventory passed=true)

    An attention_required result is an expected safety outcome for an unhealthy or still-progressing target. Do not force completion — inspect the returned observation ids and the Release audit trail.

  3. Complete only after healthy evidence 
    cargo run -p pharness-cli -- releases verify \
  --release-id "$RELEASE_ID" --complete --actor lucas \
  --reason "disposable dev release verified after completed Argo sync" \
  --timeout-ms 30000
# expect: status=verified, verified=true, completed=true, release.status=completed
  4. Confirm durable evidence and audit 
    cargo run -p pharness-cli -- releases get --release-id "$RELEASE_ID"
# expect: status=completed, post_sync_verification.status=verified,
#         post_sync_verification.runtime_ready=true

cargo run -p pharness-cli -- audit-events --resource-kind release --resource-id "$RELEASE_ID"
# expect events: release.post_sync_verified and release.completed
Current boundary of this verification

It proves a completed Argo operation plus Application health and one exact Deployment rollout (plus the bounded Prometheus inventory when the contract requires it). Loki and traces are not yet contract criteria, and image provenance is not verified here. It is blocked for production-targeted WorkItems.

Production approval

Production is a different animal from dev by design:

  • Human approval bound to the exact artifact and evidence. Production GitOps merge requires it; nothing in the pipeline auto-promotes to production. A --production-impacting WorkItem tightens approval gates throughout.
  • The same build promotes to production. One real build feeds distinct staging and production deployment records, each retaining its GitOps change, Release and registry evidence.
  • Rollback ≠ success. Successful rollback records recovered service while the requested WorkItem remains failed. Restored service after rollback does not mean the requested change succeeded.
  • Observation windows are evidence. Start the window only after exact Argo and running-image verification with fresh availability samples; start the complete stated period; never trim the first point or substitute direct health checks for telemetry.
